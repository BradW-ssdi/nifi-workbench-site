Dev test round 1

This round tests the screens we have built so far and the app frame they share. The design system is far from complete: this is a first pass to find problems in the frame, the patterns, and the handoff itself before we build more. The same guide is in docs/dev-test-round-1.md.

Not in scope

  • Real data, routes, and permissions. Links that go nowhere use #. Data is static, except the Add and Edit Condition option lists, which are the real SRTE code sets.
  • Components that have no screen yet (see the Components page for what exists).
  • Figma prototype fidelity beyond the frame: most Figma screen bodies are reference images with a working rail, header, and footer. Add Condition and Edit Condition are native, editable layers.

How to test each screen

  1. Frame. Run the checklist on screens/frame.html once, then spot check it on every other screen: the current rail item is correct, the logo returns Home, the rail state carries between screens.
  2. Keyboard only. Tab through the whole page. Focus is always visible, the order makes sense, every control works with Enter or Space, Escape closes menus, dialogs, filter panels, and rail labels, and focus returns where it came from. On list screens, open a filter chip: focus moves into its panel; Update announces the result and returns focus to the chip.
  3. Zoom. At 200% and 400% (or a 640px and 320px wide window): one column, no sideways scrolling of the page, every control reachable. Only data tables may scroll sideways, inside their own box. Dialogs stay above the header.
  4. Screen reader. NVDA with Chrome or JAWS with Chrome: the page title, one h1, landmarks (Main navigation, Breadcrumb, Footer), and every announcement in the screen's contract (sort, filter counts, page changes, errors, confirmations). For Narrator, tools/a11y-508/uia-walk.ps1 prints what Windows exposes for every control.
  5. High Contrast. Windows Settings, Accessibility, Contrast themes (or Chrome DevTools, Rendering, Emulate CSS forced-colors). Icons, focus, borders, and the current page stay visible.
  6. Dark theme. In the console: document.documentElement.setAttribute('data-bs-theme', 'dark'). Repeat the keyboard and automated checks. Text on teal turns near-black on purpose; see decision D-012.
  7. Automated. axe DevTools, or the vendored axe from the console (see docs/accessibility.md), plus the 508 harness: node tools/a11y-508/run508.cjs (see its README). We see zero axe violations on every screen in scope, in light and dark theme. Known "needs review" items on the Components page only: text on the workbench's gradient backgrounds and decorative arrow glyphs. Check those by eye.
  8. Build it. Pick one screen and build it in the app from its template and the contract in docs/dev-handoff.md. Note anything in the template or contract that was unclear, missing, or hard to do in Thymeleaf and HTMX.

Reporting

For each finding: the screen, the steps, what you expected, what happened, browser and zoom level, and a screenshot. Say whether it is a bug in the template, a gap in the contract, or a question about the design.
